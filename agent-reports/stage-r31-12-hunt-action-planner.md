# R31.12 Hunt Action Planner

Local WSL implementation. No commit, no push, no VM access, no deployment.

## 1. Goal

Build the next deterministic research-side Hunt Queue Intelligence layer on
top of R31.10 Hunt Priority and R31.11 Hunt Actionability. For each
Asset<->CVE research candidate, R31.12 selects the smallest useful next
investigation step a human bug-bounty hunter should perform, based only on
evidence already produced by the research pipeline:

    "Given the evidence already available, what is the single next thing I
     should do about this candidate?"

R31.12 is a **planner only**. It never performs the action, never executes
HTTP/browser/Nuclei/crawl/fuzz/scan/exploit, never calls an LLM, never
touches the network, Mongo, or a target, and never claims a vulnerability is
confirmed. It does not recompute R31.10 priority/score or R31.11
actionability, does not modify R29 Hunt Queue semantics, R30.1 matching
semantics or R31.9 evidence-quality semantics, and is not connected to 5J,
sealed findings, notifications or authoritative verification.

## 4. Design Decisions

- **Consume, never recompute.** The planner takes the R31.10 dict and the
  R31.11 dict as read-only inputs, plus optional explicit hints
  (`evidence_provenance`, `support_scope`, `strongest_match_type`). It never
  calls the R31.10/R31.11 engines and never re-derives a priority, score or
  actionability state.
- **Terminal states are decided first.** `BLOCKED` (either projection) ->
  `RESOLVE_BLOCKERS`; `LOW_VALUE_DEFERRED` -> `DEFER`; `IMMEDIATE_VERIFICATION`
  -> `VERIFY_EXISTING_EVIDENCE`. Only `STRONG_MANUAL_REVIEW` and
  `SUPPORTING_CONTEXT` run gap selection.
- **Gaps must be explicit.** A gap is selected only from an explicit signal:
  a canonical R30.1 blocker code, a negative R31.10 adjustment code, an R31.9
  gap line with a known prefix, an explicit inferred+unscoped
  provenance/scope state, or an explicit `strongest_match_type ==
  TECHNOLOGY`. Absent fields never become invented gaps.
- **Downgrade-only.** A defensive guard ensures that when the R31.11 state is
  `IMMEDIATE_VERIFICATION` but provenance resolves to anything other than
  `EXPLICIT` (inferred/mixed/unknown), the plan can never be
  `VERIFY_EXISTING_EVIDENCE`; it targets the selected explicit gap, or the
  inferred identity (`VERIFY_COMPONENT_IDENTITY`) / its missing scope
  (`VERIFY_SCOPE`).
- **One primary action.** The result carries exactly one closed action plus
  its rank, reason codes, evidence gap, qualitative effort and
  recommendation-confidence.
- **Additive integration.** New keys only; `hunt_priority` and
  `hunt_actionability` are passed through unmodified and remain authoritative.

## 5. Closed Action Vocabulary

`HUNT_ACTIONS` (rank, effort):

| Action | Rank | Effort | Meaning |
|---|---|---|---|
| `VERIFY_EXISTING_EVIDENCE` | 0 | LOW | Candidate is already verification-ready; verify using existing evidence. |
| `VERIFY_VERSION` | 1 | MEDIUM | Version compatibility is the explicit remaining gap. |
| `VERIFY_COMPONENT_IDENTITY` | 2 | MEDIUM | Component/plugin identity is the explicit remaining gap. |
| `VERIFY_SCOPE` | 3 | MEDIUM | Program/component scope (or provenance) is the explicit remaining gap. |
| `VERIFY_PATH` | 4 | LOW | Path relevance is the explicit remaining gap. |
| `VERIFY_PARAMETER` | 5 | LOW | Parameter usage is the explicit remaining gap. |
| `COLLECT_HTTP_EVIDENCE` | 6 | MEDIUM | HTTP/method behavior evidence is the explicit remaining gap. |
| `COLLECT_TECHNOLOGY_EVIDENCE` | 7 | MEDIUM | Technology-level evidence is the explicit remaining gap. |
| `MANUAL_REVIEW` | 8 | HIGH | Actionable for human review; no narrower explicit gap was selected. |
| `DEFER` | 9 | UNKNOWN | R31.11 says low-value/deferred (or actionability is unavailable). |
| `RESOLVE_BLOCKERS` | 10 | UNKNOWN | Terminal blockers must be resolved first. |

`estimated_effort` vocabulary: `LOW` / `MEDIUM` / `HIGH` / `UNKNOWN` (fixed
per action; no numeric estimate). `confidence` vocabulary: `HIGH` / `MEDIUM`
/ `LOW` and describes confidence in the recommendation only — never
vulnerability confidence. There are no bounty, probability, exploitability,
severity or CVSS fields.

## 6. Action Precedence

Deterministic, first match wins:

1. `BLOCKED` (R31.11 state or R31.10 `blocked`) -> `RESOLVE_BLOCKERS`.
2. `LOW_VALUE_DEFERRED` -> `DEFER`.
3. `IMMEDIATE_VERIFICATION` -> `VERIFY_EXISTING_EVIDENCE` when provenance is
   explicitly `EXPLICIT`; otherwise the non-explicit defensive downgrade.
4. `STRONG_MANUAL_REVIEW` -> selected explicit gap; no gap -> `MANUAL_REVIEW`.
5. `SUPPORTING_CONTEXT` -> selected explicit gap; no gap -> `MANUAL_REVIEW`.
6. Missing/unrecognised actionability -> `DEFER` (confidence LOW).

Gap precedence (conservative, as requested): `GAP_VERSION` >
`GAP_COMPONENT_IDENTITY` > `GAP_SCOPE` > `GAP_PATH` > `GAP_PARAMETER` >
`GAP_HTTP` > `GAP_TECHNOLOGY` > `MANUAL_REVIEW` fallback.

## 7. Evidence-Gap Rules

| Gap code | Explicit signals (read-only) | Action |
|---|---|---|
| `GAP_VERSION` | blocker `version_unknown`; R31.10 negative `VERSION_UNRESOLVED`; gap prefix `version:` | `VERIFY_VERSION` |
| `GAP_COMPONENT_IDENTITY` | blockers `component_not_observed` / `plugin_not_observed`; gap prefixes `component:` / `identity:` | `VERIFY_COMPONENT_IDENTITY` |
| `GAP_SCOPE` | R31.10 negative `INFERRED_UNSCOPED_IDENTITY`; gap prefixes `scope:` / `provenance:`; explicit `INFERRED` provenance with explicit `GLOBAL`/`NONE` scope | `VERIFY_SCOPE` |
| `GAP_PATH` | gap prefix `path:` | `VERIFY_PATH` |
| `GAP_PARAMETER` | blocker `parameter_unknown`; gap prefix `parameter:` | `VERIFY_PARAMETER` |
| `GAP_HTTP` | gap prefix `method:` | `COLLECT_HTTP_EVIDENCE` |
| `GAP_TECHNOLOGY` | blocker `generic_technology_only`; explicit `strongest_match_type == "TECHNOLOGY"`; gap prefix `technology:` (forward-compatible) | `COLLECT_TECHNOLOGY_EVIDENCE` |
| `GAP_NONE` | no explicit narrow gap selected | `MANUAL_REVIEW` fallback / terminal actions |

Confidence rules: terminal actions and single-gap selections are `HIGH`;
multiple competing gaps are `MEDIUM` (the precedence rule still selects one)
and add `MULTIPLE_GAPS_PRESENT`; no-gap `MANUAL_REVIEW` and missing/
unrecognised actionability are `LOW`; the defensive non-explicit downgrade is
`MEDIUM`.

## 8. Blocker Handling

- `BLOCKED` is terminal in both projections: either R31.11
  `actionability == BLOCKED` or R31.10 `blocked == True` -> `RESOLVE_BLOCKERS`
  with `SOURCE_BLOCKED`, `evidence_gap = GAP_NONE`, and no further refinement.
- A forged/malformed R31.11 `IMMEDIATE_VERIFICATION` on top of a blocked
  R31.10 projection still yields `RESOLVE_BLOCKERS`.
- A blocked candidate with every possible explicit gap signal still yields
  `RESOLVE_BLOCKERS`; blockers can never be overridden by gap evidence.
- Non-terminal R31.10 `DEFER` without the `blocked` flag maps to the R31.11
  state (`LOW_VALUE_DEFERRED` -> `DEFER`), not to `RESOLVE_BLOCKERS`.
- Canonical R30.1 blocker codes are also used as explicit gap signals for
  non-blocked candidates (e.g. `version_unknown` on a P2/S
  `SUPPORTING_CONTEXT` candidate selects `VERIFY_VERSION`).

## 9. Ordering Behavior

`action_order_key` is a stable, JSON-serializable list for ascending sort:

```
[action_rank, ...R31.11 action_order_key]
```

The R31.11 `action_order_key` is preserved exactly (sanitised, bounded to 16
items); if it is absent the R31.10 `tie_break_key` is used as the secondary
key instead. Identical inputs always produce identical keys; repeated
evaluation is byte-identical. No randomness, timestamps, hashes or unstable
dict ordering is used.

## 10. Privacy / Bounds Behavior

- The planner keeps its own `_safe_text` (same policy as R31.10/R31.11):
  control characters collapsed, URL userinfo redacted, bearer tokens
  redacted, secret-like `key=value` / `key: value` pairs redacted, values
  bounded to 160 chars.
- R31.9 gap lines are only inspected for known prefixes; the raw lines are
  never copied into the result. Only closed codes, bounded counts
  (`MAX_REASON_CODES = 8`, `MAX_ORDER_KEY = 16`, `MAX_GAP_LINES = 64`),
  integers and sanitised rule-version text are retained.
- Result keys: `rule_version`, `action`, `action_rank`, `reason_codes`,
  `reason`, `source_actionability`, `source_priority`, `source_hunt_score`,
  `source_rule_versions`, `evidence_gap`, `estimated_effort`, `confidence`,
  `action_order_key`, `research_only`.

## 14. Limitations / Deferred Work

- `COLLECT_TECHNOLOGY_EVIDENCE` is reachable only from an explicit
  `generic_technology_only` blocker, an explicit R30.1
  `strongest_match_type == "TECHNOLOGY"` hint, or a (not yet emitted)
  `technology:` R31.9 gap line. R31.9 currently has no technology dimension,
  so in the backend this action is expected to be rare until that evidence
  exists. Absent signals never fabricate it.
- `VERIFY_SCOPE` groups the requested "scope/provenance uncertainty"; the
  `provenance:` R31.9 gap line maps to `GAP_SCOPE` by design.
- The plan is exposed on the Asset<->CVE candidate summary
  (`hunt_action_plan`, `hunt_action_plan_rule_version`). Wiring it into the
  R29 queue schema/projection or UI is deliberately deferred because R29 must
  not be modified by this stage.
- Missing/unrecognised R31.11 actionability defers (confidence LOW) rather
  than guessing an action.
- The recommended action is an advisory planning label; it is never executed
  by this code. No HTTP request, browser action, Nuclei run, crawl, fuzzing,
  scan, exploitation, LLM call or target interaction exists anywhere in the
  new module.
- No real-corpus/Mongo run was added; all tests are hermetic and offline.
