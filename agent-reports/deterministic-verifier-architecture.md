# Phase 5I — Deterministic Verifier Architecture (READ-ONLY)

Status: ARCHITECTURE ONLY. No code modified, no tests run, no network/DNS/browser/Nuclei/subprocess/LLM/Mongo touched. No 5I implementation performed.

## 1. Executive verdict

A deterministic verifier that is the ONLY security authority for CONFIRMED / VULNERABLE / NOT_VULNERABLE / severity / finding eligibility / final classification is architecturally feasible on top of the frozen 5B–5H contracts, but it does NOT exist yet in 5H-sealed-evidence form. The current repository contains TWO parallel verification worlds that must not be confused:

- World A (legacy, live-adjacent): `ai/verification/verifier.py` (`XSSVerifier`) + `ai/verification/oracle.py` + `ai/verification/{http_executor,browser_executor,composite_executor,xss_pipeline}.py` + `ai/schemas/xss_verification.py` + `ai/schemas/xss_finding.py`. This world EXECUTES (it calls `executor.execute(attempt)` inside `verify()`), classifies into POTENTIAL / CONFIRMED / INCONCLUSIVE, and materializes `XSSFinding` directly. It is the most mature oracle/stored-round design available and the primary source of reusable rules, but it is NOT a 5I verifier: it consumes live executor output, not sealed `EvidenceRecord` / `EvidenceHandoff`, and it both executes and judges in one call.
- World B (frozen, 5E–5H sealed): `ai/schemas/evidence.py` (`EvidenceRecord`, `HttpObservation`, `NucleiObservation`, `BrowserObservation`), `ai/evidence/{builder,handoff,store,observations,index,blob_store}.py`, `ai/execution/{http_executor,nuclei_executor,browser_executor}.py`, `ai/audit/trail.py`, `ai/limits/ceilings.py`. This world is observation-only, immutable after seal, hash-addressed, and verdict-free by construction (`FORBIDDEN_EVIDENCE_FIELDS`, `extra="forbid"`). It has NO classifier at all today. 5I must be built here, reusing World A's rules but never World A's execution path.

Architecture verdict: PROCEED TO 5I IMPLEMENTATION DESIGN ONLY on the World B boundary (`EvidenceHandoff` → integrity/provenance gate → typed sealed observations → deterministic classifier → classification result → separately gated finding materialization), with World A rules ported as pure functions over sealed bytes and every legacy verdict path hard-gated. Blockers B1/B2/B4/B5 remain BLOCKED; `LIVE_BROWSER` remains False; `LIVE_NUCLEI` / `LIVE_TRAFFIC_ENABLED` remain False; no live execution is authorized by this report.

## 2. Existing verifier architecture

### 2.1 `ai/verification/verifier.py` — `XSSVerifier` (World A authority today)

- Entry: `verify(analysis: XSSAnalysisResult, plan?) -> XSSVerificationResult`. It deep-copies the analysis, builds a plan from LLM payload candidates (`_build_plan_from_analysis`), executes every attempt via injected `VerificationExecutor` (`_safe_execute`), enforces evidence binding (`_enforce_evidence_binding`: `attempt_id`/`request_url`/`request_method` must match exactly, else downgrade to ERROR), then classifies per attempt (`_classify`) and materializes findings (`_build_finding`) for statuses in `{POTENTIAL, CONFIRMED}`.
- Status vocabulary actually produced: `POTENTIAL`, `CONFIRMED`, `INCONCLUSIVE` only. `NOT_VULNERABLE` is NEVER produced — documented explicitly: "The current evidence schema does not capture the structured two-control observations that a reliable negative result would require." `XSSFinding.status` still documents `NOT_VULNERABLE` as a possible string (schema-level ambiguity, see §16).
- Confidence is a deterministic fixed map `_STATUS_TO_CONFIDENCE = {CONFIRMED: 0.95, POTENTIAL: 0.50, INCONCLUSIVE: 0.20}` — conservative, headroom-preserving. Reusable as policy shape, but it must be re-versioned under 5I (see §11).
- Confirmation states (verifier-derived, never LLM-controlled): `REFLECTION`, `SINK_REACHED`, `JAVASCRIPT_EXECUTION`, `OBSERVABLE_EFFECT`, plus stored-only `STORAGE_ATTRIBUTED`. `oracle_channels` is the sorted subset of `{E1,E2,E3}` that fired. Multiple channels never raise severity.
- Classification dispatch (`_classify`): transport failures → INCONCLUSIVE; WAF BLOCK/TRANSFORM (status or structured observation) → INCONCLUSIVE; then phase-gated: `stored_submit` (at most POTENTIAL via `_http_path_confirms`), `stored_read` (only via `_classify_stored_oracle`), legacy `stored` (at most POTENTIAL `STORAGE_ATTRIBUTED`, never confirming), `oracle` phase (only via `_classify_oracle`), plain browser (at most POTENTIAL `SINK_REACHED` — the "mandated demotion": browser chain/token evidence NEVER yields CONFIRMED), HTTP (POTENTIAL only via `_http_path_confirms`).
- HTTP confirm predicate `_http_path_confirms` (single source of truth, reused by reflected + stored paths): `reflection.reflected` AND location in `{HTML_ATTRIBUTE, JAVASCRIPT_STRING, SCRIPT_BLOCK, URL}` (plain `HTML_BODY` is explicitly weaker and does NOT confirm) AND exact `observed_correlation_token == attempt.correlation_token`. The executor's `matched_correlation_token` boolean is advisory and never trusted alone.
- Browser preconditions `_browser_preconditions_met`: browser observation present; `SourceToSinkStep.is_well_formed_chain` (parameter-first, sink-present, observable-last) plus exact parameter/step binding (`parameter_name`, `parameter_location`, `endpoint`); token independently observed as substring in a structured runtime channel; exact `observed_correlation_token` match. Executor booleans (`executed_script`, `correlation_token_in_runtime`) are advisory.
- Oracle proof `_oracle_execution_proof` (single source of truth for reflected): 7 ordered gates — (1) evidence identity binding, (2) `validate_oracle_pair` (seed 32-hex, value 16-hex, `D == W(S)`, `D != S`), (3) run freshness `oracle_seed(run_salt, oracle_identity, phase) == seed` (stale/cross-run rejected; `run_salt=None` disables oracle entirely, fail-closed), (4) candidate identity `oracle_identity == candidate.attempt_id` resolved by `logical_pair_id`, (5) same-origin final URL vs endpoint origin, (6) anti-harvest over `PreExecutionInput` ONLY (payload, bound input, intended/actual URLs — never post-execution oracle channels), (7) exact E1/E2/E3 over executor-owned channels. Reflected/unknown additionally requires the paired HTTP attempt (`logical_pair_id`) to satisfy `_http_path_confirms`; DOM/mutation requires no HTTP pair.
- Stored proof `_stored_oracle_proof` (single source of truth for stored): 9 ordered gates — both-legs identity binding; shared non-empty `round_id` + shared `oracle_identity`; pair validity + SUBMIT/READ S/D equality; freshness re-derived as `oracle_seed(run_salt, oracle_identity, "stored_submit")`; same-origin READ (final vs intended vs endpoint); strict ordering `READ.started > SUBMIT.finished` with future-skew tolerance (300 s) and unparseable/future/reversed failing closed; clean READ (no S/D/token/round/payload in either READ URL); anti-harvest over SUBMIT + READ pre-execution material; exact E1/E2/E3 over READ channels with E2 origin = READ origin. `_submit_accepted` gates READ execution (transport + WAF + status + auth/CSRF/reject markers; acceptance is a precondition, never storage proof). `discover_stored_read_url` order: Location → case endpoint → first same-origin `<a href>`; cross-origin/downgrade/unclean hints fail closed WITHOUT falling back to the endpoint; READ navigates clean (executor-side guarantee, verifier re-checks).
- Finding materialization `_build_finding`: deterministic `finding_id = "xf-" + sha256(case_id|attempt_id|status)[:32]`; preserves `knowledge_ids` only when `payload_origin == "knowledge"`; records `round_id`/`read_url` as audit metadata only; `browser_verified` currently derived from advisory `browser.executed_script` (legacy weakness, see §16); `remediation_notes` always empty.
- Audit `_build_audit`: counts by `AttemptStatus`, flags `has_browser_execution_evidence` / `has_reflection_evidence`, notes empty plans and stored-round gating notes. Accounting only, never a verdict.

### 2.2 `ai/verification/oracle.py` — trusted oracle primitives

- `S = sha256(run_salt \x00 attempt_id \x00 phase)[:16]` (32 hex), `D = hex8(fnv1a32(S)) + hex8(fnv1a32(hex8(h1)+":"+S))` (16 hex); FNV-1a over UTF-16 code units, bit-identical Python/JS (`JS_W_SOURCE`); `OraclePlanner.plan` owns S/D/snippet/payload, supports `{html_body, html_attribute, script_block, generic}` skeletons only, enforces seed-once / value-never-on-wire, double-quote safety for attribute contexts, E3 length flag at 240 chars (advisory; verifier recomputes).
- Evidence predicates: `evaluate_e1_dialog` (kind in {alert,confirm,prompt} AND exact `message == D`); `evaluate_e2_network` (non-navigation, same-origin vs endpoint, path percent-decoded ONCE then exactly `/.watch-oracle/<D>`, no suffix/prefix/second-segment, query never participates); `evaluate_e3_eval` (payload ≤ 240 else False/disabled; operator in {eval, setTimeout:string} AND exact `value == payload`; `new Function` unsupported).
- `PreExecutionInput` + `anti_harvest_violations`: D must not occur in payload/bound-input/intended/actual-URL/body/snippet/referrer/extra pre-execution inputs; payload must contain S exactly once; accepts ONLY `PreExecutionInput` (TypeError otherwise) so post-execution oracle evidence structurally cannot enter the scanner.

## 3. 5I input boundary

Preferred pipeline (normative):

```
EvidenceHandoff
  → handoff structural validation (schema version, required hashes, ID formats)
  → EvidenceStore verified read (blob bytes → re-parse → recompute triple → compare index claims)
  → integrity/provenance verification (seal hashes + bindings + AUTHZ_VALID_FOR_PROVENANCE)
  → typed sealed observations (HttpObservation | NucleiObservation | BrowserObservation, schema/version-checked)
  → deterministic verifier (pure function of sealed bytes + pinned rule/policy versions)
  → classification result (versioned, hashed, immutable)
  → [separately gated] finding materialization (only on verifier-authorized classes)
```

The verifier entry accepts ONLY `(EvidenceHandoff, EvidenceRecord-bytes-as-read, pinned verifier/rule/policy versions)`. It never accepts a live executor, a network handle, a browser handle, a subprocess handle, an LLM handle, or a caller-supplied verdict.

NEVER trust caller-supplied: `verdict`, `finding`, `severity`, `vulnerable`, `confirmed`, `confidence`, `matched`/`finding_like_text_present` as verdict, `e1/e2/e3_observed` booleans as proof, `matched_correlation_token` / `correlation_token_in_runtime` / `executed_script` booleans as proof, raw `target`/`artifact` identity strings, raw dialog/console/DOM text, Nuclei stdout text, matcher output, LLM `expected_behavior` hints, `control_request_unchanged` as a negative verdict, or any severity/confidence number from any upstream stage.

Authoritative (derived from verified evidence only): evidence_id, execution_id, authorization_id (after provenance verification), program/target tuple (after target-binding check), artifact identity + content hash (after artifact-binding check), test-plan/hypothesis/match binding, execution class/stage, sealed observation fields that survive the integrity gate, recomputed content/binding/observation hashes, marker-hash equality against locally recomputed oracle expectations, verifier version + rule ID + policy version stamped on the result.

Merely observations (never authority alone): HTTP status/headers/body samples, reflection location labels, redirect chains, Nuclei exit/stdout/stderr samples and `finding_like_text_present`, browser dialog/oracle/eval advisory booleans and raw channel text, WAF/CSP/vendor hints, `object_hint`/Location discovery hints, timestamps, audit records, LLM/researcher text of any kind.

## 4. Integrity/provenance gate

Mandatory gates in exact order (first failure wins, fail-closed, no reinterpretation):

1. Handoff structurally valid (`evidence-handoff/v1`, ID formats, all three seal hashes present, `provenance` pinned).
2. Store verified read succeeds: indexed entry exists, not tombstoned/quarantined, blob bytes present, bytes parse as `EvidenceRecord`, `verify_record` recomputes the frozen triple, triple equals both blob content and index claims, evidence/execution/authorization keys equal index keys. Any divergence → CORRUPT path (quarantine, no classification).
3. Lifecycle is SEALED (BUILDING refused — unpersistable; INCOMPLETE refused at handoff — data-state, not a negative verdict; QUARANTINED/tombstoned refused).
4. `complete == true` and required observation channel present per execution class (`REQUIRED_OBSERVATIONS`).
5. Program binding: handoff program/target tuple equals sealed bindings and provenance issuance bindings.
6. Authorization provenance: `verify_provenance_for_handoff` returns `AUTHZ_VALID_FOR_PROVENANCE` (nonce match, lifecycle ISSUED|CONSUMED, issuance window covers execution start, artifact/target/plan bindings equal). REVOKED/EXPIRED-at-start/forged/mismatched → `HANDOFF_REJECTED`.
7. Target binding: canonical host/scheme/port/path-scope equal across handoff, sealed record, and issuance.
8. Artifact binding: artifact_id + content hash equal across handoff, sealed record, and issuance; derivation/template hashes consistent with execution class (contract vs executed payload hash for browser; template hash for nuclei).
9. Execution identity: evidence_id/execution_id consistent; stage pairing valid (stored READ requires its SUBMIT leg — see §7).
10. Observation schema understood: `evidence_schema_version == "evidence/v1"`, observation class known and supported by the pinned verifier version; unknown schema/unknown class/unsupported version → explicit rejection (fail-closed), never heuristic parsing.
11. No forbidden lifecycle consumed: tombstoned, quarantined, `AUDIT_GAP`-without-record where policy requires presence, or any state the policy marks non-consumable.

Explicit fail-closed map: BUILDING → refuse (not persistable); INCOMPLETE → `HANDOFF_REJECTED` (refusal is data-state, never NOT_VULNERABLE); CORRUPT (hash mismatch, binding mismatch, missing blob, index divergence, read-back divergence) → quarantine + no classification; ORPHANED → forward-only re-index under original keys only, never served until re-verified; AUDIT_GAP → separate gap entry, sealed bytes never mutated, classification blocked where policy requires gap-free chains; unknown schema / unsupported observation class / unknown verifier-rule version → blocked/unknown result, never a guess; stale/invalid provenance → `HANDOFF_REJECTED`; malformed observation → rejection. Incomplete evidence must NEVER be reinterpreted as negative evidence ("no proof of vulnerability" ≠ "NOT_VULNERABLE").

## 5. Classification state machine

5I states (minimum, terminal states marked *): `CONFIRMED*` (confirmed positive evidence under the exact rules of §§6–9), `NOT_VULNERABLE*` (deterministic negative evidence ONLY when a future two-control negative-evidence schema + policy explicitly proves the negative — NOT IMPLEMENTED today, so this transition is currently unreachable and any attempt to emit it without that schema is a verifier bug), `POTENTIAL` (suspicious/insufficient evidence — meaningful reflection, sink-reached, weak matcher, storage-attributed — never a finding without a second gate where policy so requires), `UNKNOWN`/`INCONCLUSIVE*` (transport failure, WAF interference, binding/integrity failure, unsupported schema, ambiguous pairing, truncated observations that defeat exact matching — the safe default and the ONLY output for every gate failure).

Transition rules: every gate failure in §4 transitions to handoff-rejected/blocked without entering classification; inside classification, any single predicate failure transitions to `UNKNOWN`/`INCONCLUSIVE`, never to `NOT_VULNERABLE`; `POTENTIAL` never self-promotes to `CONFIRMED` (promotion requires a fresh, fully gated proof path, not accumulation of weak signals); `CONFIRMED` requires the complete ordered gate list of the applicable proof path with zero skips; `NOT_VULNERABLE` requires its own (currently nonexistent) complete negative-proof path. All terminal states are final for that (handoff, verifier-version, rule-version) triple — re-verification with identical inputs returns the identical result (idempotent replay, see §13).

Determinism contract: same sealed envelope bytes + same verifier version + same rule version + same policy version → byte-identical classification result, including result hash. No wall-clock, no randomness, no LLM, no network, no iteration order dependence (canonical JSON, sorted channels/sets, fixed maps).

## 6. XSS verification

Port World A's oracle proof as pure functions over sealed `BrowserObservation` + sealed derivation/binding context. Executor-owned proof channels only:

- E1 = exact dialog marker: sealed `dialog_marker_hashes` contains `sha256(exact D)` where D is locally recomputed as `oracle_value_from_seed(S)` from the sealed derivation binding (never trusting a caller-supplied D), AND the dialog kind constraint (alert/confirm/prompt) is attested in sealed evidence in a form the verifier understands. Arbitrary strings ("xss confirmed", "alert detected", "script executed", console text, DOM text, generic matcher output) are NEVER sufficient — only exact-D dialog proof counts.
- E2 = same-origin `/.watch-oracle/<D>`: sealed `oracle_event_hashes` contains the exact oracle-path event hash for locally recomputed D, AND sealed page/endpoint origins prove same-origin (decoded-once exact path `/.watch-oracle/<D>`, no suffix/prefix/second-segment, query never participates, navigations never count). Wrong-origin E2 fails closed even with exact D.
- E3 = exact eval payload marker: sealed `eval_marker_hashes` contains the exact executed-payload hash for the sealed `executed_payload_hash`, AND sealed length attestation proves the ≤240-char exact-equality precondition (truncated observations can never satisfy E3 — prefix comparison is forbidden), AND operator is in the closed set ({eval, setTimeout:string}; `new Function` unsupported).

Each of E1/E2/E3 additionally requires: marker identity binding (hash equality against locally derived expectations, not caller claims), payload-hash binding (`executed_payload_hash` equals the sealed derivation's executed hash; submitted-vs-executed identities kept separate), execution identity binding (evidence/execution IDs from the integrity gate), program/target binding (§4), artifact/test-plan binding (§4), and attempt/phase/round binding where applicable (oracle phase for reflected; `round_id` pairing for stored, see §7). Anti-harvest (D absent from all sealed pre-execution material) and run freshness (seed re-derivation under the current run binding — the 5I analogue of `run_salt`, e.g. issuance/execution binding) must both pass before E1/E2/E3 are even evaluated. Any failure → `UNKNOWN`/`INCONCLUSIVE`, never downgrade-to-`POTENTIAL`-as-proof.

## 7. Stored XSS

Preserve `SUBMIT → READ → EXECUTION` with no shortcut. Sealed-evidence form:

- Submit evidence: a SEALED `http_verification`-class record (or the SUBMIT leg of a `browser_verification` round, per the frozen stage model) satisfying the submit-acceptance gate ported from `_submit_accepted` (transport success, no WAF BLOCK/TRANSFORM, no auth-required statuses, no CSRF/reject markers; Location/meaningful-reflection/success-status as acceptance signals graded by strength). Acceptance is a precondition only — never storage proof, never confirmation.
- Read evidence: a SEALED `browser_verification`-class record whose navigation URLs (intended AND actual, sealed) are clean: they contain none of S/D/token/round-id/payload (sealed clean-READ invariant, verifier re-checked even though the executor guarantees it). A generic GET/READ response containing reflected text is NOT stored XSS — reflection in the READ leg at most supports the `STORAGE_ATTRIBUTED` (POTENTIAL-ceiling) advisory signal, never confirmation.
- Execution evidence: exact E1/E2/E3 of the round's OWN D during the READ leg, per §6, with E2 origin = READ origin.
- Round pairing: shared non-empty `round_id` (`sr-` + 32 hex), shared derivation identity, sealed `submit_evidence_ref` (content hash, not a mutable pointer) linking READ to its SUBMIT, strict ordering (READ started after SUBMIT finished; unparseable/future-skewed/reversed fails closed), same-origin READ (final vs intended vs endpoint), S/D equality across legs, freshness + anti-harvest across both legs' pre-execution material.

Deterministic round outcomes: correct-round + full proof → `CONFIRMED`; wrong-round execution (D from another round), stale READ (ordering/freshness failure), mismatched READ (round/derivation/origin mismatch), reflected-only READ (no execution proof), missing execution, duplicate attempts for one round (ambiguous pairing never guessed) → at most `STORAGE_ATTRIBUTED`/`POTENTIAL` when a genuine storage signal exists, else `UNKNOWN`/`INCONCLUSIVE`. The legacy single-pass `phase="stored"` shape, if ever encountered in sealed form, caps at `POTENTIAL` and MUST NEVER confirm.

## 8. HTTP verification

Pure function over sealed `HttpObservation`. Never performs a request. Rules:

- Positive path (ported from `_http_path_confirms`): transport outcome `responded` with 2xx-class sealed status AND meaningful reflection location (attribute / JS-string / script-block / URL — plain HTML-body reflection is insufficient) AND exact token/marker equality against a locally derived expectation (never trusting an advisory boolean). All three required; any gap → not positive.
- Expected-artifact conditions: sealed method/path/query/body bindings must equal the authorized artifact projection (translator-equivalent check at verify time: method pair, path, query bounds, allowlisted headers, body hash). Mismatch → rejection, never lenient matching.
- Redirects: sealed redirect chain (≤5 hops + overflow flag) re-validated (same-registrable-domain, same-port, no downgrade, no userinfo/controls/IP-literal destinations); cross-boundary or over-cap chains fail closed; a confirming verdict never rests on a redirect hop outside the authorized target.
- Target identity: sealed canonical target tuple from the integrity gate; evidence from any other origin is inadmissible for this handoff.
- Negative evidence: there is currently NO sealed negative-evidence schema sufficient for `NOT_VULNERABLE` (the `control_request_unchanged` stub is metadata only). Missing tokens, generic error pages, CDN/WAF pages, unexpected content, and truncated bodies (explicit `sample_omitted` / `chain_truncated` / over-budget flags) all yield `UNKNOWN`/`INCONCLUSIVE` — truncated observations must never be completed by guessing. Substring/regex/reflected-content matches are treated conservatively: matching proves reflection at most, never vulnerability; transport success (2xx) is never vulnerability confirmation.

## 9. Nuclei verification

`NucleiObservation` is ADVISORY OBSERVATION ONLY. The deterministic gate:

1. Re-validate the 5F template safety posture from sealed bindings: sealed `template_id` + `template_hash` equal the authorized artifact; `argv_digest` equals the locally recomputed closed-spec argv digest; execution class is `nuclei_scan`; target/plan bindings pass §4.
2. Treat `finding_like_text_present`, exit code, stdout/stderr samples, and any matcher-like text as untrusted data. A Nuclei matcher — however strongly worded — MUST NOT become `CONFIRMED` on its own. Weak/generic matches (status-only, short/generic tokens, regex-only without anchored specificity, any match without a sealed observed-response binding to the authorized target/artifact/plan) become `POTENTIAL` at most, and `UNKNOWN`/`INCONCLUSIVE` where the observation is truncated, ambiguous, or unattributed.
3. A `CONFIRMED`-via-Nuclei path, if ever admitted, requires a separately versioned specificity policy: exact template identity + exact matcher semantics from a closed allowlist + sealed observed response bytes exhibiting the exact expected condition on the authorized target + full provenance/binding passage + absence of WAF/generic-error confounders. Until that policy ships as a pinned, replayable rule version, the Nuclei→CONFIRMED transition stays unreachable by construction.
4. Legacy `ai/researcher/nuclei_runner.py::to_findings` (`matched = status == COMPLETED and stdout.strip() non-empty`, caller-supplied `severity`, persisted `raw_output`, `scope/presence/version` passthrough) and `ai/researcher/nuclei_pipeline.py`'s `to_findings` call + `save_findings` persistence, plus the `NucleiFinding` schema (`matched`, free `severity`, `raw_output`, `evidence` free strings), MUST be removed from authority: HARD-BLOCK any path that converts them into verifier input or finding eligibility (see §16). They may survive only as deprecated research-display helpers with no path to 5I/5J, clearly marked non-authoritative, or be deleted in a later phase — this phase changes nothing.

## 10. Finding generation boundary

Verification classification and finding materialization are separate stages with a one-way gate between them:

- The verifier outputs ONLY a versioned, hashed classification result (evidence bindings + rule/policy versions + outcome + conservative severity or severity-unset + eligible/ineligible flag). It never writes a finding, never mutates evidence, never attaches evidence to anything.
- A finding (whether the existing `XSSFinding` shape or a future sealed-finding schema) may be materialized ONLY when the classification result for that exact (handoff, verifier-version, rule-version) triple authorizes it (i.e. outcome is a finding-eligible class under the pinned policy). The materializer re-verifies the classification hash, re-checks that the underlying evidence is still SEALED/complete/valid (no stale attachment), and binds the finding immutably to: evidence_id, execution_id, authorization_id, program, canonical host, scheme, effective port, target resolution identity, scope evaluation identity, artifact identity + content hash, verifier version, verifier rule ID, evidence content/binding/observation hashes, and the classification outcome. Any mismatch → no finding.
- Forbidden at the boundary: caller-selected severity, caller-selected vulnerability class, LLM-selected confirmation, arbitrary finding fields (fixed schema, `extra="forbid"` equivalent), stale evidence attached to new findings, and any rebinding of evidence after verification. `finding_id` must be deterministic over (classification hash + evidence triple + verifier/rule versions), matching the existing `xf-` determinism pattern but extended with version pins.

## 11. Severity policy

Severity is deterministic and versioned, and no upstream severity is authoritative — not LLM, not Nuclei template metadata, not researcher suggestion, not caller input. Policy:

- Severity derives ONLY from: (a) the sealed artifact's typed vulnerability class, via (b) a fixed, pinned policy table mapping (vulnerability class × verifier rule ID × evidence strength) → severity, versioned alongside the verifier. Where the table has no entry, severity remains UNSET (explicit `severity_unset` reason) — the verifier MUST NOT guess, interpolate, or inherit a Nuclei/LLM severity.
- Conservative fallback: any `CONFIRMED` without a deterministic severity entry materializes (if at all) with severity unset/pending and the lowest handling priority the downstream policy defines for unset — never with an inflated or inherited severity. `POTENTIAL`/`UNKNOWN` never carry a confirmed-class severity.
- The existing `_STATUS_TO_CONFIDENCE` map is confidence, not severity, and must not be repurposed as severity. Confidence (if retained) needs its own versioned map; severity needs a new table. Both must be documented as non-comparable.

## 12. Verifier rule registry

A versioned, replayable registry: each classification cites `verifier_version` (the 5I classifier build), `rule_id` (the exact proof path, e.g. `xss-reflected-oracle-e1/v3`, `xss-stored-round-e2/v2`, `http-meaningful-reflection/v1`, `nuclei-advisory/v1`), `observation_schema_version` (`evidence/v1`), `artifact_schema_version`, and any `policy_version` (severity/finding-eligibility tables). Rules are pure data + pure functions: no hidden behavior, no unlogged heuristics, no LLM calls, no I/O. Unknown rule versions, schema versions the verifier does not implement, or policy versions it cannot resolve → fail closed (`UNKNOWN`/`INCONCLUSIVE` or handoff-blocked, with an explicit `unknown_rule_version` / `unsupported_schema` reason). Downgrade (accepting an older, weaker rule when a newer is pinned) is forbidden unless the pinned policy explicitly authorizes named-version replay for audit purposes — and even then the result is labeled with the actual rule version used.

## 13. Idempotency + replay

Same `(EvidenceHandoff bytes + sealed envelope bytes + verifier_version + rule_version + policy_version)` → byte-identical classification result, including a deterministic result hash (canonical JSON over the fixed result fields, same hashing discipline as `ai/evidence/hashing.py`). Duplicate verification is a no-op returning the identical result (dedupe by result hash; no counters, no state changes). Verifier results are immutable classification artifacts persisted separately from evidence (never as evidence mutation — the store has no update API and none may be added for 5I). Re-verification under a newer verifier/rule version produces a NEW result artifact citing the new versions; the old result is retained, never overwritten, so audit can replay either.

## 14. Audit

Verifier audit events (append-only, via the frozen `ai/audit/trail.py` discipline — hashes + decisions + codes, never secrets/payloads/bodies/stdout/page text/LLM text): `HANDOFF_ACCEPTED`, `HANDOFF_REJECTED` (with closed reason), `INTEGRITY_REJECTED` (hash/binding failure class, no raw bytes), `CLASSIFICATION_COMPLETED` (outcome + verifier/rule/policy versions + result hash), `CLASSIFICATION_BLOCKED_UNKNOWN` (reason class), and optionally `FINDING_MATERIALIZATION_AUTHORIZED` (finding ID + classification hash, emitted by the materializer, not the classifier). Audit is accounting only: no executor or verifier reads audit to grant permission, and audit never overrides recomputed hashes. Post-classification audit failure → separate `AUDIT_GAP` entry; classification bytes are never mutated to repair audit.

## 15. Security threat model

Adversarial review (verifier treats ALL research/LLM-derived text, page content, Nuclei output, and caller-supplied fields as untrusted data; only sealed hashes + locally recomputed expectations are trusted):

- Forged `EvidenceHandoff` (invented hashes/IDs): defeated by store verified-read + triple recomputation + index-claim comparison; forged handoffs never reach classification.
- Modified evidence bytes / hash mismatch / missing blob / index divergence: CORRUPT path — quarantine, no classification, no negative inference.
- Binding mismatch (program/target/artifact/plan/execution/stage): rejected at §4 gates; cross-program and cross-target confusion both fail closed because every gate compares all bound axes, not just IDs.
- Stale authorization (revoked/expired-at-start/forged/nonce-mismatched): `HANDOFF_REJECTED`; stale target resolution / stale scope evaluation (scope-lists-hash drift, resolution identity mismatch): rejected at target/scope binding checks — the verifier never re-resolves or re-evaluates, it only checks sealed pins.
- Forged Nuclei matcher / forged stdout text: advisory-only gate (§9); text presence never confirms; specificity policy unreachable until versioned.
- Forged browser console entry / forged dialog marker / replayed XSS marker: only exact-D executor-owned channels count (§6); console/DOM/generic text never suffices; replay across runs defeated by freshness re-derivation; replay across rounds defeated by round/derivation binding; D harvested onto the wire defeated by anti-harvest over sealed pre-execution material.
- Severity injection / finding injection (caller/LLM/Nuclei severity, hand-built findings): defeated by §10–§11 gates — severity from the pinned table or unset; findings only via authorized classification with full binding re-checks.
- LLM prompt injection embedded in evidence (payloads, pages, stdout, `expected_behavior` hints, knowledge text): never executed, never trusted for classification; LLM text is not even an input to the classifier (upstream hypotheses are untrusted data, see §16).
- Malicious artifact metadata (absolute URLs, authority overrides, OOB markers, oversized matchers): defeated at the 5E/5F translator/gate layer (already frozen) and re-checked at the verifier's artifact-binding gate; unknown artifact shapes fail closed.
- Malformed observations / schema confusion (unknown fields, wrong types, version skew): `extra="forbid"` + typed parsing + explicit version gate; unknown → blocked, never heuristically parsed.
- Verifier downgrade / rule-version confusion: pinned versions on every result; unknown or unauthorized-older versions fail closed; downgrade requires explicit policy authorization and is labeled.
- Duplicate verification / races: idempotent result-hash dedupe; immutable results; ledger CAS + index conditional-insert semantics already frozen — the verifier adds no mutable state, so races cannot promote a verdict.
- Legacy verifier bypass / legacy `to_findings()` bypass: the critical migration risk — any live path from `XSSVerifier.verify` (which executes AND judges), `NucleiRunner.to_findings`, `NucleiFinding`, or ad-hoc `XSSFinding(...)` construction to a finding store/dashboard/alert MUST be enumerated and hard-blocked at the 5J boundary (§16); 5I reads ONLY sealed handoffs, and 5J materializes ONLY from 5I-authorized classifications.

## 16. No LLM authority

5I is deterministic: no LLM calls, no LLM-derived inputs to classification, no prompt-dependent behavior. The LLM may exist upstream for research/hypothesis/interpretation/explanation/candidate-rule proposal ONLY. Its outputs — suggested payloads, `expected_behavior` hints, verification ideas, status/confidence/severity suggestions, knowledge-attributed claims — are untrusted data that never directly determine CONFIRMED / VULNERABLE / NOT_VULNERABLE / severity / finding eligibility. The boundary is structural: the classifier's input types have no LLM-text fields (any such field present on legacy schemas is ignored by the classifier and stripped before hashing), and tests must assert the classifier is unreachable from any LLM-output type without passing through sealed execution + the integrity gate.
